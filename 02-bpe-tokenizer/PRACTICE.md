# Step 2 실습 가이드 — BPE 토크나이저

## 배울 것
- 서브워드 토크나이징의 원리 (Byte Pair Encoding)
- vocab 크기와 시퀀스 길이 사이의 트레이드오프
- 토크나이저가 모델 성능·비용에 미치는 영향

## 개념 요약
1. 텍스트를 **바이트(0~255)** 시퀀스로 본다 (바이트 단위 BPE — 어떤 문자열도 표현 가능).
2. 가장 자주 붙어 나오는 **인접 쌍**을 찾아 새 토큰 하나로 합친다 (merge).
3. 원하는 vocab 크기가 될 때까지 반복한다. merge 순서 목록이 곧 토크나이저.
4. 인코딩 = 학습된 merge를 **학습 순서대로** 적용, 디코딩 = 토큰 → 바이트 → 문자열.

## 실습 순서
1. **쌍 세기**: 정수 리스트에서 인접 쌍의 빈도를 세는 함수 `get_stats`
2. **합치기**: 특정 쌍을 새 토큰 id로 바꾸는 함수 `merge`
3. **학습**: `vocab_size=512` 정도로 merge 반복 (256개의 기본 바이트 + merge 256개)
4. **encode / decode** 구현
5. **검증**: `decode(encode(s)) == s` 가 모든 입력(영어·한글·이모지·빈 문자열)에서 성립하는지
6. **압축률 측정**: `바이트 수 / 토큰 수` 를 셰익스피어 텍스트로 계산
7. **비교**: `tiktoken`의 `gpt2` 인코딩과 같은 문장의 토큰 수를 비교
8. **모델에 연결**: Step 1의 `gpt.py` 문자 토크나이저를 내 BPE로 교체 → vocab이 커졌을 때 loss·학습 속도 변화 관찰

## 확인할 것
- vocab을 키울수록 같은 텍스트의 토큰 수가 줄어든다 (압축률 상승)
- 한글 문장은 영어보다 훨씬 토큰이 많이 나온다 (바이트 단위라 한글 1글자 = 3바이트). Step 5에서 다시 다룬다.
- 주의: 토큰 단위가 바뀌면 loss 숫자는 직접 비교할 수 없다 (문자당 loss와 토큰당 loss는 다른 단위). 비교하려면 **bits per byte**로 환산해야 한다.

## 셀프 체크
1. 왜 바이트부터 시작하면 "모르는 글자(UNK)"가 없는가?
2. merge를 학습 순서대로 적용해야 하는 이유는?
3. vocab이 너무 크면 어떤 비용이 늘어나는가? (임베딩 표, 출력층 크기)
